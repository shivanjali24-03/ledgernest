# Deployment

LedgerNest runs on free tiers only: the web app on **GitHub Pages**, the API on **Render**, and PostgreSQL on **Neon**. There are three environments, one per long-lived branch, plus a demo that needs no server.

| Environment | Branch | Web app | API (Render service) | Database (Neon branch) |
|---|---|---|---|---|
| Production | `main` | https://shivanjali24-03.github.io/ledgernest/ | `ledgernest-api` | `main` |
| Staging | `staging` | https://shivanjali24-03.github.io/ledgernest/staging/ | `ledgernest-api-staging` | `staging` |
| Development | `develop` | https://shivanjali24-03.github.io/ledgernest/dev/ | `ledgernest-api-dev` | `dev` |
| Demo | `main` | https://shivanjali24-03.github.io/ledgernest/demo/ | none: sample data in the browser | none |

Merging into a branch deploys that environment automatically: the web app via the **Deploy web** workflow, the API via Render's auto-deploy. Database migrations run when the API starts.

## How it fits together

- **Web app.** GitHub Pages hosts one site per repository, so every deploy rebuilds all four environments from their branches and publishes them together ([`deploy-web.yml`](../.github/workflows/deploy-web.yml)). Each build gets its base path and API address at build time. Pages has no app routing, so a deep link like `/ledgernest/dev/users` reaches [`404.html`](../.github/pages/404.html), which sends it to the right environment, and the app puts the address back.
- **API.** [`render.yaml`](../render.yaml) defines the three services. On start each one applies new migrations (`prisma migrate deploy`), creates the first Super Admin if `SEED_SUPERADMIN_*` is set (safe to repeat), then starts NestJS. Render checks `/api/v1/health`.
- **Sessions across sites.** The web app (`github.io`) and API (`onrender.com`) are different sites, so the refresh cookie is `SameSite=None; Secure; Partitioned`. Partitioned (CHIPS) cookies keep working in browsers that block third-party cookies, because the cookie belongs to LedgerNest's page only. If a browser refuses it anyway, people stay signed in until they reload the page, then sign in again. Nothing breaks.
- **Real client IPs.** Render puts one proxy in front of the API, so `TRUST_PROXY=1`. Rate limits and the audit log then see each person's own address, not the proxy's.
- **Cold starts.** Free Render services sleep after 15 minutes without traffic, and the first request takes up to a minute. The app says so ("Waking up the server…") after 5 seconds.

## One-time setup

### 1. Neon (database)

1. Sign up at [neon.tech](https://neon.tech) (free plan) and create a project named `ledgernest`, region **AWS Asia Pacific (Singapore)**, PostgreSQL 17.
2. The project starts with a `main` branch. Create two more branches from it: `staging` and `dev`.
3. For each branch, open **Connect** and copy the connection string with **connection pooling turned off** (migrations need a direct connection). In it, change `sslmode=require` to `sslmode=verify-full`.

### 2. Render (API)

1. Sign up at [render.com](https://render.com) with GitHub and allow access to the `ledgernest` repository.
2. **New → Blueprint**, choose the repository, and apply `render.yaml`. It creates the three services.
3. Render asks for each service's secrets:
   - `DATABASE_URL`: that environment's Neon string from step 1.
   - `SEED_SUPERADMIN_EMAIL` and `SEED_SUPERADMIN_PASSWORD`: the first Super Admin (12+ characters with upper-case, lower-case and a number). Use a different password per environment.
   - Optional, to email scheduled reports: `SMTP_URL` and `MAIL_FROM` (see [INTEGRATIONS.md](INTEGRATIONS.md#email-for-scheduled-reports)). Without them reports are only kept in the app.
   - `JWT_ACCESS_SECRET` is generated by Render. Never copy it anywhere.
4. When the services are live, note their addresses from each service's page. Service addresses are unique across Render, so when a name is taken (`ledgernest-api` already is), Render adds a suffix, e.g. `https://ledgernest-api-x7k2.onrender.com`.
5. Once you've signed in as Super Admin, you can delete `SEED_SUPERADMIN_PASSWORD` from the service. The account stays.

### 3. GitHub (web app)

1. **Settings → Pages → Source: GitHub Actions.**
2. **Settings → Environments → github-pages → Deployment branches:** allow `main`, `staging` and `develop`.
3. **Settings → Secrets and variables → Actions → Variables** (these are public addresses, not secrets):

   | Variable | Value |
   |---|---|
   | `API_URL_PRODUCTION` | production service address + `/api/v1` |
   | `API_URL_STAGING` | staging service address + `/api/v1` |
   | `API_URL_DEV` | development service address + `/api/v1` |
   | `OPERATOR_NAME` | optional: who runs the service, named on the privacy notice and terms |
   | `CONTACT_EMAIL` | optional: where people write about their data (grievances under the DPDP Act) |

   Leave one empty and that environment is built as a demo.
4. **Actions → Deploy web → Run workflow** for the first deploy. After that, merges deploy by themselves.

## Releasing

Work lands in `develop` (deploys to dev). A release is a pull request `develop → staging`, checked on staging, then `staging → main`. Until a branch has had its first release, its web address shows a short "not released yet" page.

## Secrets

- Secrets live only in Render (database URLs, the JWT secret, the seed password). GitHub only holds public API addresses as variables.
- `.env` files are git-ignored. `apps/api/.env.example` lists every variable with safe example values.
- The API refuses to start with a missing or example JWT secret, a non-PostgreSQL database URL, or `SameSite=None` without `Secure`.

## Troubleshooting

| Symptom | Check |
|---|---|
| Sign-in says it can't reach the server | The API may be waking up (wait a minute), or `API_URL_*` is wrong. Open `<API>/api/v1/health`. |
| CORS error in the browser console | `CORS_ORIGINS` on the Render service must be exactly `https://shivanjali24-03.github.io` (no path, no trailing slash). |
| Signed out on every reload | The browser refused the cross-site cookie (see "Sessions across sites" above). Signing in again works. |
| Render deploy fails at start | Read the service's logs. A bad `DATABASE_URL` or a migration error shows there. |
| Invitation links point to the wrong place | `WEB_APP_URL` on the Render service. |
